# ioctls/ — Per-Subsystem ioctl() Argument Generators

Registry of kernel ioctl-driven subsystems Trinity fuzzes through the `ioctl()` syscall. One file per subsystem (device driver, virtualization interface, filesystem control plane, etc), except where a subsystem's ioctl surface was large enough to carve one class per file behind an internal header; each group declares its ioctl command table and, optionally, hand-rolled argument sanitisers for commands whose args are structs. `syscalls/ioctl.c` picks a group at dispatch time; groups don't call each other.

## Files (72 .c files + 2 internal headers, ~18,097 LOC)

Core registry/dispatch (not a per-device group):
- `ioctls.c` (294) — group registration table, fd→group matching (`find_ioctl_group`), the tiered arg-shape picker (`pick_random_ioctl` / `ioctl_arg_for_request`), `dump_ioctls()`. No `REG_IOCTL_GROUP` — this *is* the registry.
- `efault_cache.c` (320) — shm-resident EFAULT-probe cache backing Tier 2 of the arg-shape picker (see below). No `REG_IOCTL_GROUP` either; it's a support module `ioctls.c` calls into.

Largest / structurally distinct per-device files:
- `drm.c` (799) — DRM core plus vendor extensions (i915, nouveau, radeon, exynos); defines fallback structs/macros for nouveau ioctls not present in all kernel header versions (`DRM_IOCTL_NOUVEAU_GETPARAM` etc, guarded by `#ifndef`).
- `btrfs.c` (740) — btrfs filesystem ioctls (as opposed to `btrfs-control.c`, the 41-line `/dev/btrfs-control` device-manager group).
- `iommufd.c` (718) and `vfio.c` (610) — see areas of attention below; the two most heavily hand-tuned groups.
- `vhost.c` (572) — vhost-net/vsock/scsi/vdpa control ioctls.
- `firewire.c` (560) — IEEE1394 character device ioctls, 26 struct-alloc sites.
- `cdrom.c` (505) — CDROM/ATAPI command family, 23 `get_writable_struct()` sites for the various TOC/subchannel/multisession structs.
- `vduse.c` (422), `binder.c` (407), `gpio.c` (399), `cec.c` (397), `vfs.c` (390), `mtd.c` (390), `framebuffer.c` (348), `autofs.c` (337) — mid-size, each with several `sanitise_*` struct-fillers for their multi-command ioctl surface. `binder.c` carries its own copy of `<linux/android/binder.h>`-equivalent definitions (`flat_binder_object`, `binder_write_read`, etc) inline, since the header isn't part of the standard kernel-headers package trinity builds against.

Two groups are split one class per translation unit rather than living in a
single file. Each carved TU exposes exactly two symbols — a sanitiser and a
dispatcher — and the spine walks them in order:
- ALSA: `snd.c` (633, the spine plus hwdep/mixer) with `snd-oss.c` (345), `snd-seq.c` (325), `snd-ctl.c` (292), `snd-pcm.c` (284), `snd-timer.c` (215), `snd-compress.c` (124), `snd-rawmidi.c` (84) and `snd-internal.h` (49). 87 `get_writable_struct()` call sites across the cluster — by far the densest sanitiser surface in the directory.
- Virtual terminal: `vt.c` (221, the spine) with `vt-tioc.c` (272), `vt-kd.c` (251), `vt-vt.c` (183), `vt-font.c` (105), `vt-unimap.c` (71) and `vt-internal.h` (43). 32 `get_writable_struct()` sites across the cluster; the hand-built `termios2` fallback struct lives in `vt-internal.h` so both the spine's `vt_ioctls[]` and the tioc TU can name the `TCGETS2`-family request numbers.

The remaining files follow the same per-ioctl-table pattern described below, scaled to however many commands the subsystem exposes and whether any need struct-shaped args. Examples: `kvm-vm.c`/`kvm-vcpu.c`/`kvm-system.c` split KVM's ioctl surface by fd type (system fd vs per-VM fd vs per-vCPU fd); `nvme.c`, `sg.c`, `i2c-dev.c`, `mei.c`, `usbmon.c`, `pps.c`, `ptp_clock.c`, `rtc.c`, `loop.c`, `nbd.c`, `userfaultfd.c`, `seccomp.c`, `pidfd.c`, `epoll.c`, `dm.c`, `scsi.c`, `hidraw.c`, `input.c`, `joystick.c`, `videodev2.c`, `atm.c`, `socket.c`, `vsock.c`, `vmci.c`, `watchdog.c`, `rfkill.c`, `msr.c`, `hpet.c`, `mce.c`, `dmabuf.c`, `sgx.c`, `uinput.c`, `ext.c`, `tun.c`, `fuse.c`, `perf_event.c`, `random.c`.

## Key design decisions

1. **One `struct ioctl_group` per file, self-registered via constructor.** `IOCTL(x)` macro (`include/ioctls.h`) builds `{.request = x, .name = "x"}` table entries; `REG_IOCTL_GROUP(grp)` expands to a `__attribute__((constructor))` function that calls `register_ioctl_group(&grp)` at load time, so files never need to be listed anywhere centrally — dropping a new `.c` file with a `REG_IOCTL_GROUP` line is the entire integration.
2. **Group matching is fd-based, two paths.** `find_ioctl_group()` first tries every registered group's optional `fd_test(fd, &stbuf)` callback (used when devname matching is ambiguous or the fd is anonymous — e.g. `kvm_vm_fd_test()` walks the `OBJ_FD_KVM_VM` object pool rather than checking `/proc/devices`). If no `fd_test` claims the fd, it falls back to matching `devtype` (`DEV_CHAR`/`DEV_BLOCK`/`DEV_MISC`) plus device name against each group's `devs[]` list (resolved via `map_dev()`).
3. **No struct_catalog/ or args/ dependency.** Unlike other struct-producing subsystems in the tree, ioctl arg structs here are filled by hand: a `sanitise_<name>()` function calls `get_writable_struct(sizeof(*s))`/`get_writable_address(size)`, `memset()`s the whole struct to zero, then stamps only the fields the author decided matter (bounded random values, valid-looking enums, etc), leaving the rest zeroed rather than catalog-random. A static-analysis tripwire enforces the "memset before field stores" half of this pattern (`scripts/check-static/ioctl-struct-memset.sh`) because `get_writable_struct()` returns recycled pool memory that can leak previous-syscall residue back to the kernel (or be read as attacker-influenced-but-unintended field values) if left unzeroed.
4. **Three-tier arg-shape picker in `ioctls.c` (`ioctl_arg_for_request`)**, run before any per-group custom sanitiser, then overridden per-command where a custom sanitiser exists:
   - Tier 1 (decoded): if the request was built with `_IO*()` and carries a non-`_IOC_NONE` direction, trust `_IOC_SIZE()`/`_IOC_DIR()` for buffer size and read/write direction; seed with random bytes for `_IOC_WRITE`.
   - Tier 2 (EFAULT-probe cache, `efault_cache.c`): for legacy raw-constant ioctls (TCGETS-style, sockios) with no shape info in the request number, call the ioctl once with a bogus pointer arg and classify by errno (`EFAULT`→pointer, `EINVAL/ENOTTY/ENOSYS/0`→scalar, `EBADF/ENXIO`→unknown/mismatched fd). Verdict is cached fleet-wide in shm, keyed by `(group_idx, request)`, since the kernel's dispatch table is process-independent. Probes twice with different bogus values and only commits if both agree.
   - Tier 3 (legacy 50/50): coin-flip between a random scalar and a writable page, used when Tier 2 is inconclusive or the group opted out of probing.
5. **EFAULT-probe opt-out list** (`efault_cache.c`, `efault_optout_devs[]`/`efault_optout_names[]`): groups whose ioctls allocate real kernel state on the dispatch path *before* arg validation — `kvm`, `vhost-{net,vsock,scsi,vdpa}`, `iommu`, `vfio`, `loop-control` (by devname) and `kvm_vcpu` (by group name, since vCPU fds have no `/proc/devices` entry and some vCPU ioctls like `KVM_NMI`/`KVM_SMI` are side-effecting `_IO()` calls that would fire for real during a probe) — skip Tier 2 entirely to avoid leaking vcpus/rings/containers/loop devices on every probe.
6. **Post-sanitise scrub against shared regions.** `pick_random_ioctl()` and `syscalls/ioctl.c`'s `sanitise_ioctl()` both call `avoid_shared_buffer_out()` on `a3`/`a4`/`a5`/`a6` — custom sanitisers that overwrite `a3` with their own struct pointer are covered by the second scrub in `syscalls/ioctl.c`, run unconditionally after the group's `.sanitise()` returns, so a struct pointer accidentally aliasing trinity's shm bookkeeping (childdata/stats/kcov buffers) can't be handed to the kernel for `copy_to_user`.

## Integration points

- `syscalls/ioctl.c` — the actual `ioctl()` syscall entry (`sanitise_ioctl()`): picks a group via `find_ioctl_group(rec->a1)` (99% of the time) or `get_random_ioctl_group()` (1-in-100, deliberately mismatching fd and group to explore misuse), calls `grp->sanitise(grp, rec)`, then re-scrubs `a3`.
- `include/ioctls.h` — shared types: `struct ioctl`, `struct ioctl_group`, `IOCTL()`/`REG_IOCTL_GROUP()` macros, `register_ioctl_group`/`find_ioctl_group`/`get_random_ioctl_group`/`pick_random_ioctl`/`dump_ioctls` prototypes.
- `fds/kvm.c` (and analogous per-subsystem fd modules) — populate the `OBJ_FD_*` object pools that `fd_test` callbacks (e.g. `kvm_vm_fd_test`) walk to recognize programmatically-created fds with no `/proc/devices` presence.
- `utils/shm.c`/`shm` — backs both the EFAULT-probe cache (`shm->ioctl_efault_cache[]`, lock-free CAS insert) and per-group dispatch counters some groups bump (e.g. `kvm-vm.c` increments `shm->stats.kvm_vm_ioctls_dispatched`).
- `rand/random-address.c` — `get_writable_address()`/`get_writable_struct()` (pool-backed buffer allocation). Value generation comes from the header inlines/macros: `rnd_modulo_u32()`/`rnd_u64()` in `include/rnd.h`, `RAND_BOOL()`/`ONE_IN()` in `include/random.h`.
- `scripts/check-static/ioctl-struct-memset.sh` — CI-time regex tripwire enforcing the memset-before-field-store convention across every `sanitise_*` function in this directory.
- `syscalls/io_uring/io_uring_register.c` — references `pick_random_ioctl()`'s arg-scrub ordering in a comment, implying a parallel (not shared) arg-shape convention for `io_uring_register`'s own opcode table.

## Areas of attention

1. **`vfio.c` and `iommufd.c` are among the most heavily hand-tuned groups in this directory** — 17 `sanitise_vfio_*` functions (`:104` `dma_map` … `:477` `device_feature`) and 21 `sanitise_iommufd_*` functions (`:82` `destroy` … `:591` `hw_queue_alloc`) respectively, covering every multi-field struct command in both groups. Both are `_IO()`-declared (no encoded size or direction), so Tier-1 `_IOC_SIZE` carries no signal and would hand the kernel a random-shaped buffer; the sanitisers replace that path entirely and stamp each struct's `argsz`/`size` field in-band.
2. **`kvm-vm.c` documents its own struct-shaped-arg rationale in a comment**: Tier 1's `_IOC_SIZE`-based generic buffer under-sizes `kvm_irq_routing`'s flexible array tail and leaves fixed structs' fields (slot indices, alignment, `guest_phys_addr` bounds) unconstrained, so almost every dispatch would bounce on `-EINVAL` without hand-written sanitisers.
3. **ALSA is the densest sanitiser surface in the directory** — 87 separate struct-allocation sites spanning hwdep, PCM, control, timer, sequencer, mixer, rawmidi, compress and OSS-compat ioctl families. It is no longer one file: the per-class families were carved into `snd-*.c` behind `snd-internal.h`, leaving `snd.c` as a spine that walks each class's dispatcher in order. `vt.c` was carved the same way into `vt-*.c` behind `vt-internal.h`, one family per TU. Both are code-motion splits — the dispatch order and the sanitiser bodies are unchanged — and both follow the earlier by-fd-type precedents in this directory (`kvm-vm.c`/`kvm-vcpu.c`/`kvm-system.c`, `btrfs.c`/`btrfs-control.c`).
4. **EFAULT-probe side effects are opt-out by string list, not derived from the kernel.** `efault_optout_devs[]`/`efault_optout_names[]` in `efault_cache.c` is a manually maintained list; a new group whose dispatch path allocates kernel state before arg validation (a new vhost transport, a new virtualization ioctl set) silently leaks that resource on every EFAULT probe until someone notices and adds it to the list.
5. **No shared struct-generation infrastructure.** Every `sanitise_*` function hand-codes field values (bounded `rnd_modulo_u32()` calls, `RAND_BOOL()` flag picks); there is no catalog-driven or reflection-based struct filler for this directory (`grep -rn struct_catalog ioctls/` — zero hits), so field coverage and bounds-plausibility depend entirely on the judgment of whoever wrote each `sanitise_*` function, and are not automatically kept in sync with kernel struct changes.

## Summary

`ioctls.c` is a self-registering table of `struct ioctl_group`s, one per kernel subsystem file in this directory; `syscalls/ioctl.c` matches an fd to a group and lets the group's `.sanitise` callback pick a command and shape its argument. Argument generation is a three-tier fallback (decoded `_IOC_SIZE`/`_IOC_DIR` → EFAULT-probe cache → random scalar/page) for commands with no custom handler, overridden per-command by hand-written `sanitise_*` functions (memset-then-stamp-fields) where a subsystem author judged the generic tiers insufficient — a judgment applied unevenly across the directory (KVM's VM/vCPU ioctls, VFIO, and IOMMUFD are among the most heavily hand-tuned groups in the directory; coverage varies across the remaining files).
