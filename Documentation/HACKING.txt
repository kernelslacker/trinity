* Building on old distributions.
  Trinity is developed using the latest glibc/kernel, which means from time to time
  changes are introduced which may make it fail to compile on older distributions
  (especially enterprise ones).  The preferred way to fix this is to add the missing
  declarations to kernel fallback headers
  If for some reason you can't detect presence of a definition in a header file
  (or need to test prescence of a header file), add it to configure. This should
  be a last resort, in most cases an #ifndef addition to kernel fallback headers will be enough.

  `make uapi-check [KERNEL_SRC=<kernel git tree>]` finds what such a build would trip over
  before anyone has to.  KERNEL_SRC defaults to $HOME/src/kernel/git-trees/linux.  It
  installs the uapi headers of an older kernel tag from that tree into a sysroot cached
  under $XDG_CACHE_HOME/trinity-uapi (or $HOME/.cache), reruns configure against it and
  compiles trinity and the test-binary objects in build-uapi/<tag>.  The kernel tree is only
  read, nothing is linked and nothing is run.  The first run takes under a minute and leaves
  about 10MB in the cache; later runs reuse it.  It is opt-in, not part of check-static,
  because it needs a kernel tree.

  The compile keeps going past a failing file, and a failed run lists the missing symbols,
  the most widespread first, with the number of files each breaks and one example error
  (UAPI_CHECK_TOP= sets how many; default 20).  The full log is build-uapi/<tag>/build.log
  and every error, one per line, is in build-uapi/<tag>/errors.tsv.

  The tag defaults to v6.12 (override with UAPI_TAG=).  It is the 2024 longterm release,
  still maintained, and the uapi base of Debian 13 and RHEL 10.  The longterm releases
  before it are maintained too, but the tree does not carry the fallbacks they would need:
  against v6.6 dozens of files fail to compile, and more against each older release.

  This means of course that trinity will be trying to run new syscalls on older kernels
  that don't implement them, but it will only call them once. After the first -ENOSYS,
  it gets marked as "Don't run this again".  It also allows us to run and test newer
  kernels on distributions with older userspace whose header files may not define those features.

* Porting to new architectures
  - Add an include/syscalls-{archname}.h defining the syscall table in the same order as your arch
  - Add an include/arch-{archname}.h to define useful things like PAGE_OFFSET, and to #define
    SYSCALLS (SYSCALLS32 and SYSCALLS64 for a biarch arch) as the name of that table
  - If your arch starts its Linux syscalls at non-zero (like MIPS does), define SYSCALL_OFFSET
    in arch-{archname}.h
  - Add syscalls/{archname}/{syscallname}.c for your arch specific syscalls, and list that
    directory in SYSCALLS_ARCH in the Makefile.
  - Include the new headers from include/arch.h and include/arch-syscalls.h so the build picks
    the correct syscall table for your arch.  select_syscall_tables() in tables/table-copy.c
    copies it into shared memory at startup.
  That should be it.

* Adding new sanitise routines
  syscalls:
   - First, decide if it's worth adding a sanitise routine at all, or if the generic
     sanitise routines are good enough, by setting each arguments .argtype[] entry
     to an appropriate ARG_*
   - In cases where the generic routines are either insufficient, or need to be overridden,
     the .sanitise member of the syscall struct can be pointed to a routine that will
     run after the generic sanitise routines.
   - The sanitise function is passed the syscall record (rec), and overwrites rec->a1..a6
     in place once the generic routines have filled them.
   - Likewise, after the syscall is run, you may need to free up resources allocated
     in the .sanitise.  You can do this in the .post function, or in .cleanup, which runs
     unconditionally after .post.
     rec->post_state may be used to store ptrs to resources etc for retrieval later in
     .post and .cleanup.
   - Beware of 'over sanitising' and limiting the possibility for boundary conditions
     to be violated. A syscall that always succeeds is not the goal, you want to be
     exercising as many error paths as possible.

* Process model.
  On startup, the first process sets up the shm etc, and then enters
  the 'main' loop (see main/loop.c), which is responsible for..

  - initial opening of sockets/fd's.  See open_fds() in fds/fds-init.c, and the providers
    in fds/ (fds/sockets.c, fds/files.c, ...)
  - forking new children See fork_children()
  - handling those children.  See handle_child()
  - makes sure the child processes are making progress,
  - Checks to see if the kernel has become tainted.
  - assorted other 'periodic' tasks.
